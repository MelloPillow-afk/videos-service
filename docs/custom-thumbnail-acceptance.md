# Custom thumbnail acceptance (MEL-12)

Local verification on 2026-10-16 uses real HTTP, PostgreSQL, and Pillow's
JPEG/PNG/WebP decoders, with the shared object-storage boundary controlled in
tests. No thumbnail business operation, repository, or image decoder is mocked.

Custom images can be selected throughout video processing. Upload authorization
persists an isolated current THUMBNAIL attempt with a fifteen-minute expiry and
signed create-once PUT headers. Confirmation checks HEAD metadata and a bounded
read against both the declared byte count and configured 5 MiB maximum. Image
format must match the declared MIME type; decoded raster dimensions must be
1280 × 720. Dimensions are checked before pixel allocation; Pillow verification
and a real pixel load run outside the event loop. No server crop UI is added.
[Pillow decoding behavior](https://pillow.readthedocs.io/en/stable/reference/Image.html).

After validation, `upload_attempts.public_object_key` is recorded in a transaction
that rechecks current attempt and video eligibility. Only then can a create-only
public PUT begin. A second transaction rechecks eligibility before selecting the
image and recording acceptance. Concurrent confirmations reuse one immutable
output and preserve the first acceptance timestamp. A storage request whose
outcome is unknown can be retried; existing identical output is reused.

Removal clears the custom selection and invalidates current thumbnail attempts,
so replay cannot restore a removed image. A generated READY image becomes active;
otherwise its PENDING/FAILED state projects NONE/null. Generated bytes and old
custom/attempt bytes are retained for explicit video deletion; scheduled orphan
cleanup is outside scope.

`tests/integration/test_custom_thumbnails.py` verifies real formats, spoofed or
corrupt/truncated/wrong-size content, metadata mismatch, missing objects, declared
and actual limits, the inclusive 5 MiB boundary, fifteen-minute expiry,
administrator/current-role checks, cross-video/stale attempts, deleting-state
rejection, concurrent/idempotent confirmation, removal/fallback, and ambiguous
storage outcomes. Public-copy races against removal, supersession, and deletion
prove that stale results cannot become the active image and that each output key
was registered before writing. Generated HTTP cases use handwritten arrangements
with real images outside generator-owned packages.

Database result fencing does not cancel an object-store write already in flight.
An inactive copied object can remain under its registered key until explicit
cleanup. Real R2 conditional-PUT/browser-CORS proof and deletion's writer-drain or
guard policy remain separate cloud evidence gates; these local tests do not
claim production cleanup or CDN revocation.

Executed after merging source-upload and media-worker integration: `make check`
(including 45 contract examples and strict Pyright), `ag` regeneration (13
operations / 23 generated HTTP cases), Yoyo apply/reapply/full rollback, and the
complete pytest suite: **158 passed**, including 23 custom-thumbnail business
cases. Coverage was 88% across the combined implementation. Checks ran in this
ticket's isolated virtual environment.
